#### 这个文件夹是什么

`SC6113-C-Completed` 是 C 部分完工后的整合目录，只包含 B 和 C 的成果。B 的智能合约放在 `contracts/`，C 的后端与数据库放在 `backend/`。目前没有加入 D 的前端，后续只需在同级增加 `frontend/`，不需要把 B 和 C 的代码重新混在一起。

B 的合约仍然是资金、角色和业务状态的最终依据。C 不修改合约业务规则，主要处理钱包登录、链下正文、REST API、数据库查询，以及链上交易回执和事件的核验。

#### C 在本次整合中完成了什么

原来的 C 后端只能用 Mock gateway 生成模拟交易哈希。现在已经接入 B 实际提供的 ABI、三个合约地址、函数和事件，并修正了双方原本不一致的地方：

- 登录时从 `RoleManager.rolesOf` 读取角色，一个钱包可以拥有多个角色。
- 项目支持 create → accept → fund 和 create → fund → accept 两种激活顺序。
- Funding 不再自动把所有里程碑改为 InProgress；Freelancer 可以单独调用 `startMilestone`，也可以按照 B 的规则从 Pending 直接提交。
- 增加项目取消、里程碑开始、争议证据和 7 天后 Freelancer 自助领取的后端对接。
- 项目、里程碑和争议使用 B 事件产生的链上 ID，数据库另外保留本地 UUID。
- 金额保存为 ETH 字符串和 wei 字符串，避免浮点误差。
- 项目说明、提交内容、拒绝理由、争议说明、证据与裁决分别生成固定哈希，并与交易参数核对。
- 交易表和事件表保存 chain ID、合约地址、函数、区块号、交易序号及日志序号。

后端不会持有私钥。正常写入顺序为：用户通过 MetaMask 发起 B 合约交易，等待交易确认，再把 `transactionHash` 和链下正文发给 C。C 只有在发送人、目标地址、函数、参数、金额和事件均能对应时才保存数据。

#### 如何运行

打开三个 PowerShell 窗口：

```powershell
# 窗口 1
cd contracts
npm install
npm run node
```

```powershell
# 窗口 2
cd contracts
$env:SEED_DEMO='true'
npm run deploy:localhost
```

```powershell
# 窗口 3
cd backend
pnpm install
Copy-Item .env.example .env
# 将 .env 中 CHAIN_MODE 改为 evm
pnpm dev
```

Hardhat node 每次重启都会清空本地链，需要重新部署。部署完成后，应核对 `contracts/deployments/localhost.json` 与 `backend/.env` 中的三个地址。默认首轮部署地址通常相同，但不能在重新部署后想当然地沿用旧值。

2026-10-14 的本机检查结果如下：B 合约测试 32 项全部通过，C 后端 API 测试 2 项全部通过；另外启动 Hardhat 本地链、部署并执行演示流程后，B/C 真实回执集成测试 1 项通过。

集成测试实际读取了 `RoleManager` 角色，并核对真实交易的发送钱包、目标合约、函数参数和 `ProjectAccepted` 事件。它证明的是本机 Hardhat 环境中的 B/C 连接，不代表已经部署到 Sepolia，也没有覆盖 D 前端、公开域名、多台电脑或生产环境。

安装 B 的依赖时，`npm audit` 仍报告 Hardhat 开发依赖树中有 46 项问题，其中 14 项 low、9 项 moderate、23 项 high。本次没有使用可能破坏依赖兼容性的 `npm audit fix --force`。合约测试正常通过，但正式部署前仍需由组内单独检查和升级开发工具链。

#### 后续成员需要注意

D 后续调用时必须遵守 `backend/docs/B-C-INTEGRATION.md` 中的哈希格式和操作顺序。如果 D 计算的 JSON 属性顺序、日期时间或空值表示不同，合约交易即使成功，C 也会因为参数无法对应而拒绝链下记录。

E 部署时需要确定公开 RPC、网络 chain ID、三份合约地址、后端域名、CORS 和数据库方案。SQLite 适合本次单机演示；如果改为多实例服务，需要换成托管数据库并补充正式 migration。B 后续若改变函数或事件，需要重新生成 ABI，同时通知 C 和 D 更新对接代码。
